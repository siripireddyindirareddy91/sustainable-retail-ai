# Architecture

Browser → Next.js pages and route handlers → catalog/recommendation/trust engines → optional Supabase and optional LLM.

Server-rendered shell and product details complement client interaction workspaces. The fallback catalog is a versioned TypeScript dataset. Local storage persists guest collections and preferences. Supabase uses the anon key plus a validated user bearer token; RLS remains the final authorization boundary. No service-role key is used for normal user operations.

## Scoring

Default recommendation weights are preference .30, quality .20, price .15, sustainability .25 and evidence confidence .10. Every component is normalized to 0–100. Known components are weighted, missing components excluded and weights renormalized. Contributions sum to the score. Sample data confidence is intentionally low.

Sustainability weights are material .20, packaging .15, durability .15, energy .10, repairability .15, recyclability .15, certifications .05 and carbon .05. A minimum of three attributes is required. Unknown values are never silently converted to zero. Carbon measurements and certifications are absent from the demonstration dataset.

The Python model separately offers TF-IDF cosine similarity and user-neighbour collaborative scoring. It is optional offline tooling, not silently presented as the online ranking implementation. Evaluation requires held-out relevance labels and reports Precision@K, Recall@K, NDCG@K, coverage and category diversity.

## API

All responses are JSON. Zod rejects malformed inputs. Private requests require `Authorization: Bearer <Supabase access token>`. Admin writes require a server-confirmed role. The best-effort rate limiter allows 90 requests/IP/minute per runtime instance and should be replaced by shared storage for production abuse prevention.

- GET `/api/health`, `/api/categories`
- GET `/api/products?q=&category=&budget=&rating=&sustainability=&sort=&page=&limit=`
- GET `/api/products/:id`
- POST `/api/products`, PUT/DELETE `/api/products/:id` (admin)
- POST/GET `/api/recommendations`, GET `/api/recommendations/:id`
- GET `/api/explanations/:recommendationId`
- GET `/api/sustainability/:productId`, POST `/api/sustainability/assess` (admin)
- POST `/api/ai/chat`, POST `/api/ai/compare`
- POST/GET `/api/compare` (GET private)
- POST `/api/auth/signup`, `/api/auth/login`, `/api/auth/reset`
- GET/PUT `/api/auth/profile` (private)
- GET/POST `/api/wishlist`, DELETE `/api/wishlist/:id` (private)
- GET/POST `/api/preferences`, `/api/interactions`, `/api/cart` (private)
- GET `/api/admin/dashboard`, `/api/analytics/overview` (admin)
- POST `/api/admin/products`, PUT/DELETE `/api/admin/products/:id` (admin)

## Database

The migration defines all 23 requested tables. Catalog tables are public-read/admin-write. Private tables use owner-only policies; roles have no public write policy, and audit logs have no public mutation policy. User event payloads are JSONB for versioning. Source attributes and normalized scores are preserved separately. Vector columns are prepared but embeddings are not generated by default.

## Generative trust boundary

Product records remain the source of truth. Retrieval identifies query categories, budgets and descriptive terms; the deterministic answer cites those records. Optional provider prompts include only retrieved records and explicit uncertainty instructions. LLM summaries are still unverified text; structured product records remain visible and authoritative. Prompt instructions alone are not a guarantee against hallucination.
